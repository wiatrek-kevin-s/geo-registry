# geo-registry

The public registry behind **Columbus**, an open-source governed GIS MCP server. Each GIS
tool or data source is one small YAML file. A Rust CLI validates the files and builds a
searchable index (`index.json` and `registry.sqlite`) that the Columbus server downloads
to answer "what data covers this place?" and "which tool does this job?".

The registry was seeded from the *Geospatial Tool Atlas* (1,564 rows: 183 data sources,
1,381 tools). Every seeded entry is marked `review.state: seeded` until a person checks it.

It also holds **operations**: engine-neutral geoprocessing tools such as Buffer, Clip or
Zonal statistics, one file each, with the names analysts and engines use for them, their
parameters, the Columbus checks that apply and the Columbus op that runs them. Each
engine's own version of an operation (ArcPy `Buffer`, QGIS `native:buffer`, PostGIS
`ST_Buffer`) will be an **implementation** entry, generated from the engine's own tool
descriptions and mapped to its operation by people. See "Operations" below.

## Layout

```
entries/data/<id>.yaml      data sources (atlas kind "Data source")
entries/tools/<id>.yaml     libraries, applications, servers, formats, services, ...
entries/operations/<id>.yaml   engine-neutral geoprocessing operations (written by people)
implementations/<software>/    one engine's tools, generated by harvest/ (never hand-edited)
mappings/<software>/<id>.yaml  which operation a tool implements, crosswalk, differences (people)
harvest/                    one harvester per engine, and the conda-forge environments
schema/entry.schema.json    JSON Schema (2020-12) for both kinds
seed/geospatial-tool-atlas.csv   the seed spreadsheet, kept verbatim
seed/convert.py             reproducible CSV -> entries converter (Python 3.12+, PyYAML)
build/                      Rust crate "geo-registry": validate, build, search
checks/                     index compatibility, endpoint health checks, equivalence tests
.github/                    CI and the pull request template
```

## Using the CLI

```sh
cd build
cargo run --release -- validate                     # schema + ids + references
cargo run --release -- build --out ../dist          # index.json, registry.sqlite, index.sha256
cargo run --release -- search lidar --kind data --db ../dist/registry.sqlite
```

`validate` exits non-zero and prints one line per problem (`file: message`). It checks the
schema, that `id` equals the file name, that ids are unique, that `related` and
`replaced_by` resolve, that each file sits in the directory for its `kind`, and that a
recipe names an allowed Columbus tool.

`build` validates first, then writes:

- `index.json`: `{format_version, generated_at, count, entries: [card, ...]}`. A card has id,
  kind, name, summary, themes or category, region, license, access types, status, url and
  review state.
- `registry.sqlite`: table `entries` (card and full entry as JSON) and FTS5 table
  `entries_fts` over name, summary, category, themes and notes. Operations are in their
  own tables (`operations`, `operations_fts`, `implementations`), and `index.json` lists
  them under `operations`; see "Index compatibility".
- `index.sha256`: `sha256sum -c` manifest of both files. Signing is a TODO.

Set `SOURCE_DATE_EPOCH` for a reproducible `generated_at`.

## Example entries

A data entry, as generated from the atlas:

```yaml
id: txgio-lidar
kind: data
name: TxGIO lidar
summary: Texas lidar point clouds and DEMs collected under StratMap and partners.
publisher: Texas Geographic Information Office
themes:
- texas
- open-data-sources
coverage:
  region: Texas
license: LicenseRef-Public-Domain
license_original: Public domain
access:
- type: http
  url: https://www.geographic.texas.gov/stratmap/elevation-lidar.html
  auth: none
status: active
review:
  state: seeded
  source: geospatial-tool-atlas
  source_row: 1336
```

A tool entry:

```yaml
id: pdal
kind: tool
name: PDAL
category: Core libraries & formats
subcategory: Data access & IO
tool_kind: Library
summary: Point cloud translation and processing library with JSON pipelines and CLI.
open_source: 'yes'
license: BSD-3-Clause
language: C++
interfaces:
- C/C++
- Python
- CLI
call:
- python
- cli
- c-cpp
wrapped_by_columbus: false
project_status: active
url: https://pdal.io
notes: Agent can run PDAL pipelines.
also_categories:
- Point clouds, LiDAR & 3D
status: active
review:
  state: seeded
  source: geospatial-tool-atlas
  source_row: 69
```

`call` lists how an agent can drive the tool. `wrapped_by_columbus` turns true once the
Columbus server ships a governed wrapper for it. `project_status` is the upstream project's
health. `status` is the health of the entry itself.

## Seeded vs reviewed

| | `seeded` | `reviewed` |
|---|---|---|
| Source | `seed/convert.py` from the atlas row in `review.source_row` | a person, through a PR |
| `access` | the atlas URL, usually a landing page (`type: http`) | real endpoints (`ogc-wfs`, `stac`, `ept`, ...) that were tested |
| `coverage`, `publisher` | inferred conservatively, often `Unspecified` / `Unknown` | checked against the publisher |
| `recipe`, `last_verified` | absent | present where useful |

The Columbus server can show seeded entries but should treat them as leads, not
verified sources. To review one, fix the fields, test each access URL, set
`last_verified`, and change `review.state` to `reviewed`. Leave `source` and
`source_row` in place.

Until the seed is retired, `entries/` must match `python seed/convert.py` output, and CI
fails on drift. To review a seeded entry, add an override in `seed/overrides/<id>.yaml`
(the fields to replace) and regenerate, in the same PR. See CONTRIBUTING.md.

## Operations

```yaml
id: buffer
kind: operation
name: Buffer
aka: [buffer zone, proximity zone, offset polygon, Pairwise Buffer]
summary: Polygons covering everything within a given distance of the input features.
group: vector/proximity
inputs:
  - { name: layer, type: vector }
outputs:
  - { name: output, type: vector, geometry: polygon }
parameters:
  distance: { type: length, required: true }
  unit: { type: enum, required: true, values: [m, ft, us-ft, km, mi] }
  dissolve: { type: boolean, default: false, note: Merge all buffers into one shape. }
  segments: { type: integer, default: 8, note: Segments per quarter circle; more is smoother. }
checks: [crs.measure, geometry.valid]
pitfalls:
  - A planar buffer of data in a geographic CRS is in degrees unless the engine switches to geodesic.
columbus: { tool: vector_op, op: buffer }
status: active
review: { state: draft }
```

- Today: 42 operations: the 16 ops Columbus's `vector_op` and `raster_op` run, plus
  `table-to-points`; then `centroid`, `convex-hull`, `difference`, `union-overlay`,
  `symmetric-difference`, `multipart-to-singlepart`, `polygons-to-lines`,
  `lines-to-polygons`, `voronoi`, `nearest-join`, `count-points-in-polygon`,
  `select-by-location`, `merge-layers`, `rasterize`, `raster-to-polygons`, `contour`,
  `resample-raster`, `mosaic`, `idw-interpolation`, `focal-statistics`, `fill-sinks`,
  `flow-accumulation`, `measure-area`, `measure-length` and `create-grid`, which Columbus
  can run through engine plugins and `run_tool`.
- A port with `many: true` takes a list (the rasters of a mosaic, the layers of a merge).
- Ids are hyphenated slugs. `columbus` records the Columbus tool and op in Columbus's own
  names (`vector_op` / `spatial_join`), so neither project has to rename anything; an
  operation Columbus has no op for leaves it out.
- Input, output and parameter names follow Columbus's where Columbus has the operation.
- `checks` are Columbus verification check ids (`crs.measure`, `join.unmatched`, ...).
- `broader` / `narrower` must name operations; `related` may name any entry.
- `review.state` is `draft` (written, not yet checked by a person), `harvested` (generated
  by a harvester) or `reviewed`. Data and tool entries keep `seeded` / `reviewed`.
- Search them with `geo-registry search "repair geometry" --kind operation`.

## Implementations

An implementation is one engine's tool: `gdal vector buffer`, `shapely.buffer`,
`st_buffer`. They are **harvested**, never typed: each script in `harvest/` asks its
engine to describe its own tools (GDAL's `--json-usage`, PostGIS's catalogue, Python
introspection) and writes `implementations/<software>/<id>.yaml` with the parameters,
types, defaults, choices and, for SQL, every overload. Today: about 6,500 tools from
more than 50 packages: GDAL, PDAL, PostGIS (geometry and raster), QGIS Processing, GRASS,
WhiteboxTools, Shapely, GeoPandas and about 40 more Python packages (rasterio, pyproj,
the PySAL family, osmnx, momepy, Apache Sedona, ...), R's sf and terra, Turf.js,
TauDEM and LAStools. DuckDB spatial and RustGIS are harvested by the weekly Engines
workflow; ArcGIS Pro has a harvester that runs on a machine with Pro. See
[harvest/README.md](harvest/README.md), including what is not harvested yet and why.

What a person knows goes in `mappings/<software>/<id>.yaml`, merged at build time:

```yaml
id: gdal-vector-buffer
implements: buffer
crosswalk:
  layer: input
  output: output
  distance: distance
  unit: { fixed: crs-units, note: Distance is in the layer's CRS units; convert it first. }
  dissolve: { fixed: false, note: No dissolve; union the output afterwards. }
  segments: quadrant-segments
differences:
  - Distance is in the layer's CRS units, so data in a geographic CRS is buffered in degrees.
effects: { modifies_input: false, network: false }
review: { state: draft }
```

- The **crosswalk** maps each canonical parameter or port to the engine's: a parameter
  name, `#N` for an unnamed SQL argument, or an object with `param` and `values`
  (translation), `unsupported`, `fixed` (the engine has no argument and always behaves
  one way; `crs-units` means a distance is in the CRS's units), `pass: values` (the
  column's values, not its name) or `repeat: 2` (the engine takes the value twice, as
  one list: a cell size given as x and y resolution).
- **presets** fixes engine arguments for this operation (`operation: intersection` for
  `gdal vector layer-algebra`).
- **variant_of**: when one tool does several operations by its arguments (`gdal vector
  layer-algebra` as intersect, union, difference; `r.slope.aspect` as slope and aspect),
  each further operation gets a mapping named `<tool id>--<suffix>` with `variant_of:
  <tool id>`. The build copies the harvested entry under that id and applies the
  variant's operation, crosswalk and presets; nothing from the tool's own mapping carries
  over.
- A mapping without `implements` can still carry a warning in `notes` (`gdal vector
  dissolve` is not the Dissolve operation).
- Validation checks every crosswalk against both sides: the operation's parameters and
  the engine's harvested ones. After a re-harvest, a stale mapping fails with the file
  and the parameter.
- `checks/equivalence.py` runs every mapped GDAL, Shapely, GeoPandas, PostGIS, QGIS, GRASS,
  WhiteboxTools, Turf.js, rasterio, rioxarray, xarray-spatial, rasterstats, dask-geopandas, sf and
  terra implementation on the same small inputs (vector shapes, a tilted elevation raster)
  and compares the results; an engine that cannot honour a value is reported as skipped
  with the reason. A behaviour difference the tests found is recorded on the mapping and
  listed in `KNOWN_DIFFERENCES`, so the run reports it ("differs") instead of failing. Apache
  Sedona, which needs Spark, has no runner yet; its mappings are checked against the
  harvested parameters only.

Search them with `geo-registry search "buffer" --kind implementation`.

## Index compatibility

Columbus servers download the index from the rolling `index` release and read the
`entries` table. Changes to the index are therefore **additive**: the `entries` table,
`entries_fts`, the `meta` keys `format_version`, `generated_at` and `count`, and
`index.json`'s `entries` and `count` keep their meaning, and hold data and tool entries
only. New kinds go in new tables and new keys. A change that existing readers would
misread (renaming `kind: tool`, for example) needs a `format_version` bump, released only
after Columbus accepts both versions. CI builds `main` and the change and runs
`checks/index_compat.py` on the two: existing tables, indexes, meta keys, `index.json` keys
and card fields must be unchanged, unless `format_version` was raised.

## Recipes are declarative

A data entry may carry a `recipe`: the Columbus tool to use (`query_features`,
`vector_op`, `raster_op`, `pointcloud_pipeline` or `registry_fetch`) and a few
plain-language steps. Recipes are never code. The schema rejects shell, scripts and
inline programs in steps, and the server only maps steps onto its own audited
operations. Adding an access URL on a **host not already in the registry needs
maintainer approval**, because the server may fetch from any host listed here.

## Contributing

Contributions go through pull requests. The template asks for an **access test**: the
command you ran against each URL, what came back, and the date. **Regional stewards** look
after entries for their area (for example Texas, or the US federal sources) and review PRs
that touch it. See [CONTRIBUTING.md](CONTRIBUTING.md).

`main` only accepts pull requests whose required checks pass: the seed converter check,
the Rust build, tests, validation and index compatibility on Linux and Windows, and the
equivalence tests. Pull requests may be set to merge automatically once those pass.
Data review decisions (setting `reviewed`), breaking index changes and anything about
ArcGIS Pro are merged by a person, never automatically.
